# Посібник користувача Solarman Hub

**Solarman Hub — незалежний аматорський проєкт. Він не пов’язаний із SOFAR (SofarSolar).**

Цей посібник допоможе налаштувати Hub, підключити логер і за потреби використовувати ESP32 Companion. Вибір мови в Hub змінює мову панелі й посібника. Companion має власний англомовний інтерфейс.

## [hub] Користування Hub

Увійдіть із паролем вебпанелі або токеном адміністратора. Панель показує вимірювання та стан логера, хмари, MQTT і локального сховища. Перевіряйте і з’єднання логера, і час останнього вимірювання: підключений логер міг ще не надіслати звіт.

Змініть мову біля індикатора оновлення. Браузер запам’ятає ваш вибір.

У **Огляді** виберіть логер і **Останнє вимірювання** або **Історія**. Історичні зразки зберігають початкові назви полів, одиниці та версію профілю. Натисніть назву вимірювання, щоб відкрити часовий графік. Виберіть проміжок часу, переміщуйте вказівник над графіком або керуйте повзунком точок із клавіатури. Перерви приймання розривають лінію; зменшення кількості точок зберігає мінімуми та максимуми.

У **Налаштуваннях** спочатку збережіть зміни, а потім виберіть **Застосувати й підключити знову**. Поточні сеанси закриються, щоб логери підключилися з новими налаштуваннями. Зміна адреси або порту прослуховування також потребує перезапуску Hub і відповідного зіставлення портів Docker.

**Пристрої** розрізняють значення, виявлені в кадрах, і виробника та модель, зазначені в обраному профілі. Відсутні відомості позначаються як невиявлені. Налаштована модель не доводить автоматичного визначення обладнання.

## [install] Встановлення та перше підключення

**Автоматичне встановлення VM**

Виконайте цю команду як **root у Shell вузла Proxmox**, а не всередині VM. Майстер проведе вас крок за кроком. Перед підтвердженням перевірте підсумок.

```sh
bash -c "$(wget -qLO - https://raw.githubusercontent.com/ordigital/solarman-hub/main/scripts/proxmox-vm.sh)"
```

Введіть адресу IPv4 з маскою (наприклад `192.168.1.50/24` або `192.168.1.50/255.255.255.0`) або залиште поле порожнім для DHCP. Шлюз і DNS запитуються лише для статичної адреси.

Майстер запитає вільний ID VM, назву, сховище диска, сховище типу каталог для Cloud-Init snippets, мережевий міст/VLAN, DHCP або статичну IPv4 (адресу/префікс, шлюз і DNS), ресурси, необов’язковий файл відкритого SSH-ключа та пароль вебпанелі щонайменше з 8 символів. Типово: Debian 13, 2 vCPU, 2 ГБ RAM і диск 20 ГБ. Він перевірить SHA-512 офіційного образу й встановить Docker та наявний проєкт Compose у новій VM. За потреби додасть тип вмісту snippets до сховища, зберігши решту типів. Наявні VM не змінюються.

Використовуйте Docker Compose. У Proxmox простим рішенням є невелика віртуальна машина Debian з Docker; не встановлюйте програму безпосередньо на гіпервізор. Програма також працює з Python 3.12 або новішим.

У каталозі репозиторію:

```sh
docker compose up -d --build
docker compose exec hub solarman-hub token --data-dir /data
```

Відкрийте `http://SERVER_IP:8080`. Токен зберігається у `/data/admin-token.txt` і не змінюється після перезапуску чи оновлення. Новий створюється лише за відсутності файлу, наприклад у порожньому томі даних. Типовий опублікований порт логера — `10000/TCP`. Якщо використовується наявний контейнер, запущений через `docker run`, Compose ним не керує: використовуйте його фактичну назву, наприклад:

```sh
docker exec solarman-hub solarman-hub token --data-dir /data
```

Альтернативне зіставлення портів хоста запобігає конфліктам:

```sh
HUB_LOGGER_PORT=18899 HUB_WEB_PORT=18080 docker compose up -d --build
```

Додайте числовий **серійний номер логера**, а не інвертора. За потреби обмежте IP джерела й зарезервуйте її в DHCP. Виберіть сумісний профіль декодування, збережіть і застосуйте. Нова інсталяція не приймає невідомі серійні номери логерів. У налаштуваннях віддаленого TCP-сервера логера вкажіть IP хоста Hub та опублікований порт логера. Докладні кроки наведено нижче в розділі «Перенаправлення власного логера: локальний сервер V5».

Для роботи без Docker:

```sh
python3 -m venv .venv
.venv/bin/pip install .
.venv/bin/solarman-hub serve --data-dir ./data
# In a second terminal:
.venv/bin/solarman-hub token --data-dir ./data
```

Для постійної інсталяції Python використовуйте менеджер процесів. `solarman-hub check-config --data-dir ./data` перевіряє конфігурацію та посилання на профілі.

## [cloud] Пересилання до хмари, локальні ACK і MQTT

Типова адреса хмари — `access3.solarmanpv.com:10000`. Hub пересилає оригінальні байти V5 та відповіді хмари. Йому не потрібні пароль облікового запису Solarman, cookies або пароль Wi-Fi. Кадри досі містять ідентифікатори пристроїв і метадані протоколу; це приватні дані установки.

ACK повідомляє логеру, що звіт отримано. Для підтримуваних звітів Hub надсилає хмарний ACK або, якщо з’єднання з хмарою не вдалося чи перевищено час очікування, один локальний ACK. Потім він закриває невдалий хмарний сеанс та ігнорує запізнілі ACK. Невідомі дійсні кадри можуть проходити далі, але не отримують локального ACK. Трафік рухається в обох напрямках, зокрема команди з хмари виробника.

Якщо Інтернет недоступний, але LAN працює, локальні показники й MQTT можуть продовжувати роботу. **Звіти, підтверджені локально під час збою, не завантажуються до хмари автоматично пізніше. Хмарна історія може мати прогалини.** Зупинка Hub перериває налаштований шлях пересилання. Повертаючись до прямого хмарного сервісу, відновіть початкові адреси призначення логера.

Для Home Assistant підключіть обидві програми до одного MQTT-брокера. У Hub введіть хост і порт брокера, необов'язкові ім'я та пароль і налаштування TLS; увімкніть MQTT Discovery. У HA налаштуйте офіційну інтеграцію MQTT. Токен API HA не потрібен. Перевірка брокера перевіряє з'єднання та автентифікацію, а не ACL публікації.

Discovery з'являється після першого сумісного зразка. Стабільні ідентифікатори датчиків використовують серійний номер логера та ID поля. Доступність MQTT, вік останнього показника логера та з’єднання з хмарою відстежуються окремо. Самостійно виберіть відповідні лічильники енергії на панелі енергії HA. Зміна брокера або префікса тем може потребувати видалення застарілих збережених тем Discovery на старому брокері.

## [history] Історія, графіки та зберігання

Історія вимірювань зберігається у `/data/history.sqlite3`. Проблеми сховища не зупиняють пересилання до хмари. Старі архіви вимірювань JSONL імпортуються один раз у фоновому режимі, поки нові звіти продовжують надходити. Перебіг імпорту й помилки сховища перевіряйте в **Конфігурації**.

Установіть **Зберігання історії** в днях і **Обмеження розміру історії** у МБ. Діють обидва обмеження; перше досягнуте видаляє найстаріші дані. Вік визначається часом отримання, тому неправильний годинник інвертора не збереже дані назавжди. Нуль днів вимикає лише обмеження віку. Вимкнення історії припиняє нові записи, але не видаляє збережену історію.

Обмеження розміру охоплює базу, її журнали та резерв для обслуговування. Тимчасові записи можуть ненадовго його перевищувати, тому залишайте вільне місце на диску. Необроблені кадри, архіви JSONL і журнали подій мають окремі обмеження. **Зменшення ліміту історії видаляє старі дані.** Спочатку створіть копію даних, які хочете зберегти.

Графіки використовують час зразка, якщо він доступний, інакше час отримання. Різні версії профілів не дають поєднати несумісні масштаби чи одиниці. Для великих проміжків повертається не більше 1500 відібраних точок; якщо перевищено ліміт сканування, звузьте проміжок. Зразки поза порядком можуть з'явитися в історії, не замінюючи найновіші поточні дані. Повторні зразки зберігаються лише один раз.

## [devices] Відомості про пристрої та профілі декодування

Hub спостерігає серійний номер логера й IP вузла з сеансу V5/TCP. Перевірені формати рукостискання LSW3 можуть показувати прошивку; підтримуваний звіт Sofar HYD містить серійний номер інвертора. Для кожного декодованого значення показано джерело й час спостереження. Hub не визначає MAC-адресу з TCP-з'єднання та не вгадує довільні текстові поля.

Вбудований профіль Sofar HYD G3 декодує 48 полів зі звіту довжиною 2115 байтів, перевіреного на установці HYD 15KTL-3PH/LSW3. Інше обладнання потребує незалежної перевірки. Самої відповідності коду й довжини недостатньо для доказу семантичної сумісності.

Профілі зберігаються у форматі JSON і містять: код, довжина повного кадру, зіставлення часу та поля. Зсув нуль — перший байт `A5` повного кадру V5. Поля задають зсув, ширину, порядок байтів, знаковість, масштаб, одиницю та необов'язкові класи HA. Посилання на регістр — примітка, а не команда опитування.

Клонуйте вбудовані профілі для редагування. Перш ніж призначити карту, скористайтеся переглядом HEX і порівняйте кілька зразків із незалежними показниками. Інший формат V5 може потребувати лише профілю; інший протокол передачі потребує коду. **Лише пересилання** передає дані без декодування.

На сторінці профілів імпортуйте окремий профіль JSON або пакет ESP32. Перевірте підсумок, стан перевірки та конфлікти. Імпорт зберігає профіль і, де доречно, новий запис логера; він не застосовує зміни й не переналаштовує логер. Чернетки сирих слів явно не перевірені та не мають вигаданих одиниць або енергетичних класів.

## [spoofing] Перенаправлення власного логера: локальний сервер V5

Щоб отримувати звіти локально, змініть налаштування віддаленого сервера логера на Hub або Companion. У цьому посібнику «спуфінг» означає використання локального сервера замість хмарного.

Для звичайної роботи:

```text
Logger → Hub → manufacturer cloud
             ↘ local history and MQTT
```

Для тимчасового аналізу:

```text
Logger → ESP32 Companion → Hub → manufacturer cloud
```

### Зміна віддаленого сервера логера

Наведені кроки призначені для логера LSW3 із прихованою сторінкою налаштувань сервера. Назви меню та поведінка після перезапуску можуть залежати від прошивки.

1. **Знайдіть обидві адреси.** У списку клієнтів DHCP маршрутизатора знайдіть IP-адреси LAN логера та сервера Hub. Наприклад, логер може мати `192.168.100.205`, а Hub — `192.168.100.50`; замініть приклади власними адресами. Зарезервуйте обидві. Адреса логера відкриває його налаштування, а на адресу Hub надсилатимуться звіти. У Proxmox використовуйте адресу VM Debian для Hub.
2. **Спочатку підготуйте Hub.** У **Налаштуваннях** додайте числовий серійний номер логера, виберіть сумісний профіль, збережіть і виберіть **Застосувати й підключити знову**. Якщо хочете зберегти передачу до хмари, увімкніть пересилання, використовуючи початкову хмарну адресу логера. Перевірте порт логера, опублікований Docker; типовий — `10000/TCP`.
3. **Відкрийте налаштування самого логера.** У браузері в тій самій LAN відкрийте `http://LOGGER_IP/config_hide.html`, замінивши `LOGGER_IP` адресою логера. Увійдіть з обліковими даними адміністратора логера, а не обліковим записом Solarman чи токеном Hub. На перевіреному логері заводські ім’я користувача й пароль — `admin` / `admin`. Якщо вони не підходять, перевірте наклейку або інструкцію чи зверніться до установника; якщо пароль змінювали, використовуйте поточний. Прихована форма завантажується всередині цієї сторінки; якщо відкрити `hide_set_edit.html` безпосередньо, налаштування можуть не завантажитися або не зберегтися.
4. **Збережіть копію обох конфігурацій серверів.** Перед змінами запишіть усі значення в **Server A Setting** і **Optional Server Setting(B)**, зокрема IP-адресу, доменне ім’я, порт і тип з’єднання. Допоможуть знімки екрана. Збережіть ці дані, щоб відновити пряме передавання до хмари.
5. **Налаштуйте основну адресу.** У **Server A Setting** введіть IP-адресу LAN Hub у **IP address**, очистіть **Domain name**, введіть опублікований порт логера Hub у **Port** і виберіть **TCP** у **Connection**. Зазвичай це робить Hub адресою A. Використовуйте порт логера, а не порт вебпанелі `8080`, порт `8899` чи приватний IP контейнера Docker. Спочатку не змінюйте B, якщо прошивка не потребує резервного варіанта нижче.
6. **Збережіть кожну змінену форму.** A і B мають окремі кнопки **Save**. Збережіть A, а якщо змінювали B — збережіть і його окремо. Знову відкрийте налаштування та перевірте збережені значення.
7. **Перезапустіть логер.** Спочатку скористайтеся його функцією перезапуску. Деякі прошивки зберігають старий TCP-сеанс навіть після запиту з панелі. Якщо логер і далі надсилає дані за старою адресою, фізично перезапустіть лише логер і лише тоді, коли його інструкція дозволяє зробити це безпечно. Не змінюйте робочі налаштування інвертора й не від’єднуйте його кабелі живлення.
8. **Перевірте фактичні звіти.** У Hub переконайтеся, що логер підключився, нові вимірювання мають актуальний час і продовжують оновлюватися. Самого з’єднання недостатньо. Якщо пересилання до хмари ввімкнено, перевірте, чи Hub отримує хмарні підтвердження (ACK), а потім — чи з’являються нові показники на хмарній сторінці виробника. Зачекайте звичайний інтервал звітування логера.

### Якщо вашому LSW3 потрібен резервний сервер B

На перевіреній прошивці LSW3 встановлення лише A на Hub не забезпечувало надійного надсилання. Працювало таке налаштування:

| Налаштування | Сервер A | Сервер B |
|---|---|---|
| IP address | IP-адреса LAN Hub | IP-адреса LAN Hub |
| Domain name | Порожньо | Порожньо |
| Port | `10001`, без служби, що прослуховує цей порт | Опублікований порт логера Hub, зазвичай `10000` |
| Connection | TCP | TCP |

A навмисно спрямовано на закритий локальний порт, щоб логер перейшов на B. **B — резервна адреса, а не друга одночасна копія кожного звіту.** Переконайтеся, що вибраний порт A ніхто не прослуховує. Збережіть обидві форми окремо, перезапустіть логер і повторіть перевірку вимірювань та хмари. Така поведінка стосується перевіреної прошивки; використовуйте її, якщо звичайне налаштування A не працює.

### Повернення до прямого передавання у хмару

Відновіть усі початкові налаштування A і B, зокрема доменні імена, порти й типи з’єднань. Збережіть кожну форму та перезапустіть лише логер. Перш ніж зупиняти Hub, перевірте нові вимірювання у хмарі виробника. Звіти, локально підтверджені під час перерви, пізніше не завантажаться до хмарної історії.

### Companion між логером і Hub

Увімкніть на Companion рівно одне з’єднання із сервером: Hub або хмарою. Не намагайтеся дублювати звіт до обох. Якщо використовується Hub, спочатку дозвольте серійний номер логера та використовуйте опублікований TCP-порт Hub. Тайм-аут підключення Companion становить 3 секунди. Налаштовуваний тайм-аут ACK за замовчуванням — 30 секунд (10–120 секунд); із Hub він має бути довшим за весь час підключення, ініціалізації та очікування ACK у Hub. Без сервера Companion локально підтверджує відомі кадри; у хмару вони не доставляються.

Для локальних ACK потрібен правильний час. Зазвичай його надає NTP; відкриття інтерфейсу Companion також передає час браузера, якщо годинник ще не налаштовано. Поки часу немає, Companion не підтверджує звіт, щоб логер міг повторити спробу.

## [esp32] Прошивання та налаштування ESP32 Companion

Надана збірка призначена для **класичного ESP32 із 4 МБ flash**, перевіреного на сімействі ESP32-D0WD-V3. Це не образ для ESP32-C3, S2 або S3. Живіть плату розробки через USB; вона спілкується через Wi-Fi.

Готові образи й контрольні суми містяться в `firmware/esp32-companion/dist/`:

- `factory.bin`: перше встановлення через USB із завантажувачем і таблицею розділів;
- `firmware.bin`: образ лише програми для OTA;
- `SHA256SUMS`: хеші цілісності.

Використовуйте USB-кабель, що передає дані. Встановіть засіб прошивання у віртуальному середовищі та визначте правильний порт:

```sh
python3 -m venv .esp-tools
.esp-tools/bin/pip install esptool==5.6.0
.esp-tools/bin/python -m esptool --port /dev/ttyUSB0 flash-id
sha256sum -c firmware/esp32-companion/dist/SHA256SUMS
.esp-tools/bin/python -m esptool --chip esp32 --port /dev/ttyUSB0 write-flash 0x0 firmware/esp32-companion/dist/factory.bin
```

Для доступу до послідовного порту може знадобитися членство в системній групі доступу. Закрийте монітори порту перед прошиванням. Якщо автоматичний вхід у завантажувач не вдався, утримуйте BOOT під час запуску інструмента й відпустіть після підключення. Заводське прошивання може скинути збережені налаштування; OTA їх зберігає.

Також на **хості Linux із Docker Engine** можна прошити пристрій безпосередньо з одноразового контейнера. Клонуйте або завантажте цей репозиторій і виконайте команди з його кореневого каталогу. Закрийте монітори послідовного порту, підключіть ESP32 до цього хоста Docker і визначте його послідовний пристрій; `/dev/ttyUSB0` — приклад:

```sh
ls -l /dev/serial/by-id/
ESP_PORT=/dev/ttyUSB0 docker compose --profile tools run --rm --build esp-flash flash-id
ESP_PORT=/dev/ttyUSB0 docker compose --profile tools run --rm esp-flash
```

Перша команда збирає інструмент і перевіряє підключений чип без запису. Друга перевіряє контрольну суму доданого образу й записує `factory.bin` за адресою `0x0`. Замініть `ESP_PORT` шляхом плати `/dev/ttyUSB…`, `/dev/ttyACM…` або `/dev/serial/by-id/…`. Інструмент не потребує Python на хості й працює окремо від Hub. Для наступних оновлень використовуйте OTA, щоб зберегти налаштування.

USB має бути доступним **на машині, де працює демон Docker**, а не лише на комп’ютері з вебпанеллю. У віртуальній машині Proxmox спочатку передайте їй USB-пристрій. Ця команда призначена для Docker Engine у Linux; Docker Desktop у Windows/macOS за замовчуванням не надає послідовні пристрої таким способом. У цих системах використовуйте наведені вище нативні інструкції esptool або явно налаштуйте передачу USB.

На сторінці **ESP32 / Прошивання** Hub після входу також доступні завантаження **Прошивка для першого встановлення через USB**, **Прошивка для оновлення OTA** і **Контрольні суми SHA-256**. Вебпанель завантажує файли; вона не прошиває пристрій через USB-порт комп’ютера з браузером.

Читайте послідовний вихід USB зі швидкістю **115200 baud**. Під час запуску виводяться унікальні SSID і пароль налаштування та ім'я адміністратора `admin` з унікальним паролем. Підключіться до точки доступу налаштування й відкрийте `http://192.168.4.1`. Введіть облікові дані адміністратора у вікні браузера. Налаштуйте домашні SSID і пароль та збережіть. Плата перезапуститься; знайдіть її IP у LAN через вихід USB або DHCP чи спробуйте `http://solarman-companion.local`.

Режим приймача слухає `10000/TCP`. Укажіть дозволений серійний номер логера, за потреби виберіть сервер і спрямуйте логер на IP ESP32. Приймач підтримує один активний логер, чотири повідомлення в черзі та кадри до 4096 байтів. Буфер кадрів, звіт і пасивне захоплення містяться в RAM та втрачаються після перезапуску.

Для збирання з джерел використовуйте PlatformIO з `firmware/esp32-companion/platformio.ini`.

## [export] Експорт профілів, налаштувань і захоплень

У **Profile builder and exports** Companion отримайте звіт, потім завантажте відому карту HYD, неперевірену чернетку сирих слів або збережений власний профіль. Чернетка показує до 64 сирих слів; визначте значення, порядок байтів і масштаб, порівнюючи кілька зразків та незалежні вимірювання. Прошивка не може автоматично визначити електричний зміст зашифрованих пакетів або довільних байтів.

Відредагуйте JSON і збережіть власний профіль на платі або завантажте профіль безпосередньо. Сховище власного профілю обмежене 12 KiB і 128 полями. Завантажте пакет імпорту Hub, щоб включити запропонований запис логера та стан перевірки. Додавання сирого зразка необов'язкове, оскільки він розкриває ідентифікатори пристроїв. Імпортуйте файл у Hub, перевірте й збережіть, а коли будете готові — явно застосуйте налаштування.

**Download ESP32 settings (without passwords)** експортує назви мереж, режим і параметри захоплення та з'єднання із сервером. Паролі Wi-Fi та адміністратора не включені. Зберігайте файл як довідку конфігурації; повторно введіть секрети під час відновлення на очищеній платі. OTA зберігає налаштування NVS і профіль у flash.

У пасивному режимі налаштуйте MAC логера та BSSID цільової точки доступу. Прив'язка ESP32 до точки доступу логера допомагає в mesh-мережах: його єдиний радіомодуль 2,4 ГГц захоплює канал станції та точки доступу. Класичний ESP32 не захоплює радіоканал 5 ГГц. Якщо логер перейде до іншої точки, оновіть цільову точку або захоплюйте новий канал.

Завантажений PCAP містить обмежений знімок приблизно 32 KiB; найстаріші пакети перезаписуються, а втрати черги підраховуються. Часто зберігайте дані під час аналізу, особливо при перепідключенні логера. Захищені кадри Wi-Fi залишаються зашифрованими. Розшифрування WPA2 на комп'ютері зазвичай потребує правильного ключа Wi-Fi та відповідного захопленого рукостискання; для WPA3 це не гарантується. Використовуйте Wireshark і зберігайте захоплення приватно. Див. [посібник Wireshark із розшифрування](https://wiki.wireshark.org/HowToDecrypt802.11).

## [ota] Оновлення OTA та відновлення

Завантажте відповідний `firmware.bin` Companion, перевірте його хеш і відкрийте **Firmware update (OTA)**. За стабільного живлення завантажте один образ програми. Не завантажуйте `factory.bin` через OTA. Засіб оновлення перевіряє вхід і дані образу про чип та продукт і активує новий образ лише після завершення завантаження.

Під час завантаження захоплення й пересилання призупиняються, тому логер може перепідключитися. Невдале або перерване завантаження зберігає поточну програму й відновлює роботу. Успішне завантаження перезапускає ESP32. Якщо нова програма не запускається, прошивка автоматично не повертається до попередньої версії. Відновіть плату через BOOT/USB і заводський образ.

OTA використовує HTTP зі входом адміністратора. Образи прошивки не підписані криптографічно, тому використовуйте перевірені файли й оновлюйте лише в довіреній LAN. Будь-хто з паролем адміністратора може встановити прошивку. Зберігайте пароль та експортовані захоплення приватно.

## [operations] Резервне копіювання, усунення несправностей та обмеження

Щоб задати або змінити пароль вебпанелі, виконайте ці команди в каталозі проєкту Compose. Використовуйте щонайменше 8 символів. Hub зберігає хеш із сіллю в `/data/admin-password.json`, а не сам пароль. Перезапуск активує зміну й закриває наявні вебсеанси. Токен адміністратора залишається чинним для відновлення доступу та API.

```sh
docker compose exec hub solarman-hub password --data-dir /data
docker compose restart hub
```

За зупиненої служби створіть копію всього тому Hub `/data`, зокрема SQLite, конфігурації, профілів, токена й архівів. Для змонтованих каталогів збережіть UID/GID `10001`. Не використовуйте `docker compose down -v`, якщо потрібно зберегти дані. Конфігурація містить пароль MQTT відкритим текстом з обмеженими правами файлової системи; відповіді API його приховують.

Використовуйте журнали та лічильники сховища на панелі, а також:

```sh
docker compose logs --tail 100 hub
docker compose restart hub
```

Справний стан служби означає, що вебсервер відповідає; стан хмари й MQTT перевіряйте окремо. Повний диск, повільне сховище або заповнені черги можуть спричинити прогалини в записах, хоча пересилання триває. Кількість відкинутих зразків дивіться в лічильниках сховища.

Якщо дані не надходять, перевірте IP і порт призначення, зіставлення Docker, DHCP, список дозволених серійних номерів і фактичний перезапуск логера. Саме рукостискання не є звітом вимірювання. Якщо поля не декодуються, перевірте код профілю, довжину, часові позначки й HEX. Старі зразки не роблять логер актуальним. Якщо графік порожній, перевірте проміжок і версію профілю. Якщо ESP32 недоступний, перевірте його точку доступу налаштування, канал, вихід USB і живлення.

Тримайте HTTP-інтерфейси Hub і Companion у довіреній LAN або VPN. Для віддаленого доступу до Hub використовуйте зворотний HTTPS-проксі з `HUB_COOKIE_SECURE=1`. Не відкривайте неавтентифікований приймач V5 TCP публічному Інтернету. Перевірки серійного номера й IP — це засоби контролю LAN, а не надійна автентифікація пристрою.
