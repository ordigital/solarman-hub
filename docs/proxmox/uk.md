## Автоматичне встановлення VM

Виконайте цю команду як **root у Shell вузла Proxmox**, а не всередині VM. Майстер проведе вас крок за кроком. Перед підтвердженням перевірте підсумок.

```sh
bash -c "$(wget -qLO - https://raw.githubusercontent.com/ordigital/solarman-hub/main/scripts/proxmox-vm.sh)"
```

Введіть адресу IPv4 з маскою (наприклад `192.168.1.50/24` або `192.168.1.50/255.255.255.0`) або залиште поле порожнім для DHCP. Шлюз і DNS запитуються лише для статичної адреси.

Майстер запитає вільний ID VM, назву, сховище диска, сховище типу каталог для Cloud-Init snippets, мережевий міст/VLAN, DHCP або статичну IPv4 (адресу/префікс, шлюз і DNS), ресурси, необов’язковий файл відкритого SSH-ключа та пароль вебпанелі щонайменше з 8 символів. Типово: Debian 13, 2 vCPU, 2 ГБ RAM і диск 20 ГБ. Він перевірить SHA-512 офіційного образу й встановить Docker та наявний проєкт Compose у новій VM. За потреби додасть тип вмісту snippets до сховища, зберігши решту типів. Наявні VM не змінюються.

Встановлення може тривати кілька хвилин. Потім відкрийте показану адресу `http://VM_IP:8080` і введіть вибраний пароль. Logger, профіль, хмару та MQTT налаштуєте в панелі; скрипт не змінює logger. Для DHCP зарезервуйте адресу VM; для статичної адреси виберіть вільну IP поза діапазоном DHCP. Дані консолі й команда отримання токена відновлення зберігаються на хості в `/root/solarman-hub-VMID-access.txt`, доступному лише root. SSH приймає ключі, а не паролі. Через 15 хвилин очікування завершується, але VM працює далі, а встановлення повторюється щохвилини. Діагностика: `qm terminal VMID`, потім у Debian `journalctl -u solarman-hub-install`.

Зберігайте Cloud-Init snippet разом із резервною копією VM. Його шлях указаний у файлі доступу; він містить хеші паролів і, за наявності, відкритий ключ. Перед міграцією чи відновленням файл має бути доступний на цільовому вузлі. Скрипт підтримує Proxmox VE 8/9 на amd64, мости Linux і сховище типу каталог для snippets. Конфігурація має автоматичні тести, але створення VM на справжньому хості Proxmox ще не перевірене. Перед запуском можна переглянути [код скрипту](../../scripts/proxmox-vm.sh).

## Встановлення вручну

Цей посібник допоможе встановити Solarman Hub у віртуальній машині **Debian 13 (Trixie), amd64** на Proxmox. Створіть VM у вебінтерфейсі Proxmox, а всі наведені команди виконуйте **всередині Debian**.

## 1. Створіть VM

1. Завантажте [офіційний ISO Debian netinst amd64](https://www.debian.org/distrib/netinst). У Proxmox виберіть вузол → сховище з підтримкою ISO → **ISO Images → Upload**.
2. Натисніть **Create VM**, назвіть її `solarman-hub` і виберіть завантажений ISO у **OS**. Почніть із **2 vCPU, 2048 MB RAM і диска 20 GB**; це рекомендовані ресурси, а не виміряні мінімуми. Виберіть віртуальний диск у сховищі, що резервується. Довша історія потребує більше місця.
3. У **Network** виберіть **VirtIO** та наявний міст LAN, зазвичай `vmbr0`. Використовуйте ту саму доступну LAN/VLAN, що й логер; назва мосту й VLAN можуть відрізнятися на різних хостах.
4. Завершіть створення, запустіть VM і відкрийте **Console**. Встановіть Debian без графічного середовища. Виберіть стандартні системні утиліти; сервер SSH необов’язковий. Під час встановлення задайте пароль root для використання консолі root нижче.
5. Після встановлення від’єднайте ISO і завантажтеся з віртуального диска. У VM → **Options** увімкніть **Start at boot** і **QEMU Guest Agent**. Після ввімкнення агента вимкніть і запустіть VM, щоб його віртуальний канал став доступним; пакет агента буде встановлено на наступному кроці.
6. Зарезервуйте адресу VM у налаштуваннях DHCP маршрутизатора. Дізнайтеся поточну адресу командою `hostname -I` у Debian. Використовуйте її всюди, де в посібнику вказано `VM_IP`. Вона відрізняється від адрес керування Proxmox і логера.

Проєкт рекомендує звичайну VM для передбачуваної роботи Docker і резервного копіювання та відновлення всієї VM. Docker у LXC потребує додаткового налаштування хоста й контейнера; це не описаний тут шлях для початківців. Див. [офіційну документацію контейнерів Proxmox](https://github.com/proxmox/pve-docs/blob/master/pct.adoc).

## 2. Встановіть Docker у Debian

Увійдіть як **root** у консолі VM Debian. У новій інсталяції Debian 13 виконайте:

```sh
apt update
apt install -y docker.io docker-cli docker-compose docker-buildx git ca-certificates qemu-guest-agent curl
systemctl enable --now docker
systemctl start qemu-guest-agent
docker compose version
docker buildx version
```

Останні команди мають показати версії Compose **v2** і Buildx. Це [пакети Docker Debian 13](https://packages.debian.org/trixie/docker.io), зокрема [Compose v2](https://packages.debian.org/trixie/docker-compose) та [Buildx](https://packages.debian.org/trixie/docker-buildx); додатковий скрипт встановлення не потрібен. Не змішуйте їх із пакетами Docker CE. Якщо Docker CE вже встановлено, залиште його й дотримуйтеся [офіційних інструкцій для Debian](https://docs.docker.com/engine/install/debian/) замість встановлення цих пакетів. Debian 12 має інші версії пакетів; цей рецепт призначений для Debian 13.

## 3. Завантажте й запустіть Hub

```sh
git clone https://github.com/ordigital/solarman-hub.git /opt/solarman-hub
cd /opt/solarman-hub
docker compose up -d --build --wait --wait-timeout 120
docker compose ps
docker compose exec hub solarman-hub token --data-dir /data
```

Перше збирання завантажує залежності й може тривати кілька хвилин. Дочекайтеся запуску `hub`; його стан має стати `healthy`. Остання команда показує токен адміністратора. Зберігайте його в таємниці. Подальші команди виконуйте в тому самому каталозі, щоб Compose знайшов той самий проєкт і том даних. Токен не змінюється після перезапуску чи оновлення, поки зберігається том даних.

## 4. Перше підключення та мережа

Відкрийте **`http://VM_IP:8080`** на комп’ютері в LAN і увійдіть із токеном. Додайте числовий **серійний номер логера**, виберіть сумісний профіль, збережіть і застосуйте. Потім установіть віддалену TCP-адресу логера на **`VM_IP:10000`**. Спочатку збережіть початкові налаштування серверів. Поведінка A/B залежить від прошивки, а після зміни може знадобитися перезапуск; якщо звіти не надходять, зверніться до посібника.

| З’єднання | Призначення |
|---|---|
| Логер → Hub | IP VM, TCP `10000` |
| Браузер → панель | IP VM, TCP `8080` |
| Hub → хмара | Налаштовані хост і порт хмари, типово `access3.solarmanpv.com:10000` |
| Hub → MQTT | Хост/порт наявного брокера; зазвичай `1883` або TLS-порт брокера |

Для встановлення та пересилання до хмари VM також потребує робочого DNS, правильного годинника й доступу до Інтернету. MQTT потребує окремого брокера, наприклад того, що вже використовує Home Assistant; цей файл Compose не створює брокер. Увімкніть інтеграцію MQTT у HA і налаштуйте той самий брокер у Hub.

Якщо ввімкнено брандмауер Proxmox, гостьової системи або маршрутизатора, дозвольте відповідний трафік від логера та вашої керівної LAN. Опубліковані Docker порти можуть обходити правила UFW гостьової системи; застосуйте обмеження на межі Proxmox/маршрутизатора або за допомогою документованого механізму брандмауера Docker. Не перенаправляйте порти Hub з Інтернету. За описаного мостового підключення LAN перенаправлення портів хоста Proxmox не потрібне. Використовуйте IP VM, а не приватний Docker IP контейнера.

Щоб зберегти альтернативні опубліковані порти після оновлень, створіть `/opt/solarman-hub/.env` перед запуском Hub:

```dotenv
HUB_WEB_PORT=18080
HUB_LOGGER_PORT=18899
```

Потім повторно виконайте `docker compose up -d --wait --wait-timeout 120` і використовуйте `http://VM_IP:18080` та адресу логера `VM_IP:18899`. Залиште типові налаштування прослуховування панелі: ці змінні змінюють порти, відкриті Docker. Зберігайте `.env` приватно.

## 5. Перевірка й усунення несправностей

Із `/opt/solarman-hub` усередині VM:

```sh
docker compose ps
curl --fail http://127.0.0.1:8080/health
docker compose logs --tail 100 hub
```

Якщо опублікований вебпорт змінено, замініть `8080`. Справна HTTP-точка підтверджує роботу служби, а не підключення логера. Окремо перевіряйте в панелі підключення логера, останнє вимірювання, хмару й MQTT. Вимірювання з’являться, коли дозволений логер надішле сумісний звіт. Зберігайте сирі журнали й експорти приватно; вони можуть містити ідентифікатори пристроїв.

Якщо `docker compose` відсутній, перевірте, чи система — Debian 13 і чи успішно встановлені `docker-cli` та `docker-compose`. Якщо `hub` завершив роботу, перевірте його журнали перед запитом токена. Якщо браузер не підключається, перевірте поточну IP VM, міст/VLAN, брандмауер і опублікований порт. Зарезервуйте адресу, перш ніж спрямовувати на неї логер.

## 6. Резервне копіювання, оновлення та відновлення

Іменований том Compose `hub-data`, змонтований у `/data`, зберігає токени, налаштування, профілі та історію в каталозі даних Docker цієї VM. Перебудова контейнера зберігає його. **Ніколи не запускайте `docker compose down -v` і не видаляйте цей том, якщо хочете зберегти дані.** Не розміщуйте його в тимчасовій файловій системі та не виключайте його віртуальний диск із резервного копіювання.

Для простої узгодженої копії виберіть VM → **Backup → Backup now**, окреме сховище копій і режим **Stop**. Це ненадовго зупинить VM і збір даних; переконайтеся, що потім вона працює. Заплануйте регулярні копії VM у Proxmox і перевірте відновлення. Сам знімок не є резервною копією. Копії містять облікові дані, тому обмежте доступ. Див. [документацію Proxmox із копіювання та відновлення](https://github.com/proxmox/pve-docs/blob/master/vzdump.adoc).

Перед оновленням створіть копію. Потім усередині VM:

```sh
cd /opt/solarman-hub
git pull --ff-only
docker compose build --pull hub
docker compose up -d --wait --wait-timeout 120
docker compose ps
```

Це оновлює джерела й перебудовує локально встановлений образ; цей спосіб не передбачає опублікованого образу Hub. Заміна контейнера ненадовго перериває пересилання. Не змінюйте назву чи каталог проєкту Compose і не видаляйте том під час оновлення. Оновлення безпеки Debian/Docker керуються окремо через APT.

Для відновлення вимкніть пошкоджену VM і відновіть вибрану повну копію VM через Proxmox. Під час запуску відновленої копії залиште початкову VM вимкненою, щоб не конфліктували IP-адреси, сеанси логера та ID клієнтів MQTT. Перевірте адресу LAN, стан служби й останній отриманий зразок. Дані після створення копії втрачаються; звіти, локально підтверджені під час збою, автоматично до хмари не додаються.

## 7. Необов’язкова передача USB для ESP32

Звичайна робота Hub не потребує ESP32 або USB. Для необов’язкового інструмента прошивання підключіть плату до хоста Proxmox і виберіть VM → **Hardware → Add → USB Device**. Виберіть цю плату й передайте її; за потреби перезапустіть VM. У Debian перевірте фактичний шлях пристрою:

```sh
ls -l /dev/serial/by-id/
```

Потім дотримуйтеся **ESP32 / Прошивання** в панелі Hub або [посібника користувача](../../src/solarman_hub/guides/uk.md). USB, підключений лише до комп’ютера з панеллю, недоступний для VM. Сам вебконтейнер Hub не отримує привілеїв USB; прошивання виконує окремий одноразовий інструмент Compose. Заводське прошивання може скинути налаштування плати.
